# 設計書レビュー結果

レビュー日: 2026-08-24 / 対象: docs/design.md (2026-08-06版)
利用者想定: 編集メンバー3人。将来 Web サービス化の可能性あり。

総評: 技術選定の数値根拠・実測検証は十分で、全体構造は妥当。ただし**実装すると壊れる矛盾が2件**(R-1, R-2)、仕様の欠落が2件(R-3, R-4)ある。以下、設計書に反映済み。

---

## 要修正(設計書に反映済み)

### R-1: `input_fingerprint` の定義が GC と矛盾する【最重要】

§5.2 は指紋を「上流**成果物ハッシュ** + params」と定義するが、§6.2 で中間 FLAC は GC される。GC 後は上流成果物が存在しないため下流の指紋が計算できず、stale 判定(§5.3「設計の要」)が崩壊する。

**修正**: N-5 の決定性(同入力・同パラメータ→同出力)を前提に、指紋を再帰定義にする:

```
fp(stage) = sha256(fp(upstream stages) + canonical_json(params))
fp(ingest) = sha256(原素材の実バイト sha256 + params)
```

成果物バイトは指紋に含めない。これで (a) GC 後も指紋が計算可能、(b) ステージごとに数百 MB を再ハッシュするコスト(FLAC 化後でも 1 ステージ約 1GB、数秒×毎回)も消える。

### R-2: `alimiter` は True Peak リミッターではない

§7 Stage 5 は alimiter を「True Peak リミッター」と記述するが、ffmpeg の alimiter はオーバーサンプリングを行わない**サンプルピーク**リミッター。インターサンプルピークは -1.0dB 天井を通過しうる。

**修正**: 実質の TP 保証は loudnorm 2パス目の `TP=-1.5`(こちらは真の TP 制御)が担い、alimiter は「その後段の安全網(サンプルピーク)」と位置づけを訂正。-1.5 → -1.0 の 0.5dB マージンでインターサンプル超過を吸収し、最終検証は §12.2 の `ebur128` 実測(TP ≤ -1.0 dBTP を assert)が受け持つ。処理は変えず、記述と検証責任を正す。

### R-3: `project.json` の並行書き込みにロックがない

§4.1 の asyncio.Lock は「同時1ステージ」用。しかし実際は (a) 複数ロールの並行チャンクアップロード、(b) ステージ完了時の書き込み、(c) 承認操作、が同一 `project.json` を read-modify-write する。tmp+rename はクラッシュ耐性であって競合排除ではないため、**最後の書き手が他の更新を巻き戻す**。

**修正**: プロジェクトごとに asyncio.Lock を持ち、`project.json` の全 read-modify-write をその中で行う(§5.1 に追記)。単一 uvicorn プロセス前提なのでプロセス間ロックは不要。

### R-4: 同期後の共通タイムラインが未定義

Stage 1 は補正の掛け方(adelay/atrim/rubberband)のみで、補正後の各トラックの**基準原点と長さ**が未定義。Stage 4 の `amix` は既定 `duration=longest` で暗黙にパドされるが、話者ごとの録音開始・終了は数十秒ずれうるため、仕様として明示しないと A/B 比較・波形表示の時間軸も揃わない。

**修正**: 「reference の t=0 を共通原点とし、3話者を同一長(3本の補正後長の最大)に無音パド/トリムして出力する」を Stage 1 の出力仕様として明記。

## 改善(設計書に反映済み)

### R-5: 話者間ラウドネス整合は loudnorm ではなく測定+`volume` で行う

§7 Stage 2-8 の「loudnorm 2パス(linear) で -20 LUFS」には2つの問題がある:

1. loudnorm は linear=true でも TP 制約でゲインが頭打ちになると**無告知でダイナミックモードに落ちる**。中間段で音を潰すのは §7 Stage 5 で自ら排した失敗モード。
2. loudnorm は最重フィルタ(実測 53x)。話者3本 × 2パスで約 2.2分。

ここで必要なのは「一定ゲインで -20 LUFS に置く」ことだけなので、`ebur128` で Integrated を測定し `volume=<差分>dB` を適用する(純線形・決定論的・TP フォールバック無し)。測定1パスで済み約1.1分短縮。ピーク管理は §6.1 どおり mix 入力ゲインと Stage 5 が担う。loudnorm の 2パス運用は最終マスタリング(Stage 5)専用とする。

### R-6: オフセット適用はサンプル単位指定にする

`adelay` のミリ秒指定は整数丸めで ±0.5ms の量子化誤差を持ち、残差目標 ±1ms の半分を適用段で使い切る。`adelay=<n>S`(サンプル数指定)/ `atrim=start_sample=<n>` を用いれば適用誤差は ±0.5 サンプル(±10µs)になる。実装時に 4.4.2 での `S` サフィックス挙動を実測確認する(§3 の検証方針どおり)。

### R-7: `python-multipart` は削除できる(依存 4 → 3)

multipart が要るのはフォームエンコードの解析のみ。チャンクアップロードを `application/octet-stream` の raw body(`await request.body()`)で受ければ不要。§6.3 のチャンク方式なら最初から multipart を使う局面がない。

### R-8: API 表記の不整合

§6.3 は「`POST …/chunk?offset=`」、§8 は「`PUT …/chunk?offset=`」。冪等な位置指定書き込みなので `PUT` に統一。

## 留意(設計書は変更せず、実装・運用で対応)

- **R-9: reference は VoIP 録音であり、ジッタバッファ適応による非線形な時間ジャンプが入りうる。** 線形ドリフトモデル+外れ値除去付きフィットで概ね吸収できるが、残差 >±1ms 警告の原因候補として UI の警告文言に含める。区間別オフセット系列に不連続(>20ms の段差)があれば個別に警告する。
- **R-10: preview.opus 96kbps は NR の失敗モード(水中音)の判定には余裕が薄い。** Opus 96k は音声にはほぼ透明だが、A/B の目的が「アーティファクト検出」である cleanup ステージだけはビットレートを上げる余地を残す(パラメータ化しておく)。
- **R-11: `GET /download/{artifact}` はパス・トラバーサル対策必須。** artifact 名はホワイトリスト(project.json に記録された成果物名)との照合のみで解決し、パス結合をしない。
- **R-12: 将来の Web サービス化への影響は小さい。** 認証はリバースプロキシ層で後付け可能、ストレージはプロジェクトディレクトリ単位で独立しているためオブジェクトストレージへ移行可能、API は既に REST。現設計のまま進めてよい。ただし project-id はユーザー入力をそのままパスにせず生成 ID にする(R-11 と同根)。

## 是認(検討の上、変更不要と判断)

- バックエンド必須の論証(5,273MB > タブ上限)、DB/ジョブキュー/WebSocket/audalign の不採用理由: いずれも数値根拠が妥当。
- rubberband によるドリフト補正: atempo が ppm 級で無効という実測は決定的で、代替なし。
- `aloop` 回避(1.3GB RAM)と `-stream_loop` 方式、`amix normalize=0`、2段コンプ、2パス loudnorm(マスタのみ): 妥当。
- 容量設計 3.5GB・処理時間 10〜15分の見積り: 実測ベースで妥当。R-5 でさらに約1分短縮。
