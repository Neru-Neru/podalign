# podalign 設計レビュー記録

対象: [docs/design.md](design.md) / 実施: 実装着手前(2026-08-24) / 利用者想定: 編集メンバー3人、将来 Web サービス化の可能性あり

実装前に設計書へ行ったレビューの記録。指摘はすべて現行の設計書に反映済みであり、
本書は「どこが落とし穴で、なぜ現在の形に決めたか」の判断根拠を残すために独立した文書として保持する。
各項目は **落とし穴 → 採用した設計** の形で読める。

総評: 技術選定の数値根拠・実測検証は十分で、全体構造は妥当。ただし初稿には
**実装すると壊れる矛盾が2件**(R-1, R-2)、仕様の欠落が2件(R-3, R-4)あった。

## 要修正と判断した指摘(設計に反映済み)

### R-1: ステージ指紋を「上流成果物のハッシュ」で定義すると GC と矛盾する【最重要】

**落とし穴**: stale 判定に使う `input_fingerprint` を「上流ステージの成果物バイトのハッシュ + params」と
定義すると、中間 FLAC を GC(設計 §6.2)した瞬間に上流成果物が存在しなくなり、下流の指紋が
計算できず stale 判定(設計 §4.3「設計の要」)が崩壊する。

**採用した設計**: 決定性(N-5: 同入力・同パラメータ→同出力)を前提に、指紋を再帰定義にする:

```
fp(stage) = sha256(fp(upstream stages) + canonical_json(params))
fp(ingest) = sha256(原素材の実バイト sha256 + params)
```

成果物バイトは指紋に含めない。これで (a) GC 後も指紋が計算可能、(b) ステージごとに数百 MB
(FLAC 化後でも 1 ステージ約 1GB)を毎回再ハッシュするコストも消える。→ 設計 §4.2

### R-2: `alimiter` を「True Peak リミッター」と扱ってはいけない

**落とし穴**: ffmpeg の alimiter はオーバーサンプリングを行わない**サンプルピーク**リミッターであり、
インターサンプルピークは -1.0dB 天井を通過しうる。これを TP 保証の主体に据えると
「TP ≤ -1.0 dBTP」の出力目標が実は保証されていない、という状態になる。

**採用した設計**: 実質の TP 保証は loudnorm 2パス目の `TP=-1.5`(こちらは真の TP 制御)が担い、
alimiter は「その後段の安全網(サンプルピーク)」と位置づける。-1.5 → -1.0 の 0.5dB マージンで
インターサンプル超過を吸収し、最終検証は `ebur128` 実測(TP ≤ -1.0 dBTP を assert、設計 §12.2)が
受け持つ。処理チェーンは変えず、保証の責任分担を明確化した。→ 設計 §7 Stage 5

### R-3: `project.json` の並行書き込みには専用ロックが要る

**落とし穴**: 「同時1ステージ」の実行ロックだけでは足りない。実際は (a) 複数ロールの並行
チャンクアップロード、(b) ステージ完了時の書き込み、(c) 承認操作、が同一 `project.json` を
read-modify-write する。tmp+rename はクラッシュ耐性であって競合排除ではないため、
**最後の書き手が他の更新を巻き戻す**。

**採用した設計**: プロジェクトごとにロックを持ち、`project.json` の全 read-modify-write をその中で
行う。ステージ実行はワーカースレッド上なので asyncio.Lock ではなく `threading.Lock` を使う。
単一 uvicorn プロセス前提なのでプロセス間ロックは不要。→ 設計 §4.1

### R-4: 同期後の共通タイムラインを仕様として明示する

**落とし穴**: Sync を「補正の掛け方(adelay/atrim/rubberband)」だけで定義すると、補正後の
各トラックの**基準原点と長さ**が未定義になる。Stage 4 の `amix` は既定 `duration=longest` で
暗黙にパドされて一見動くが、話者ごとの録音開始・終了は数十秒ずれうるため、A/B 比較・
波形表示の時間軸が揃わない。

**採用した設計**: 「reference の t=0 を共通原点とし、3話者を同一長(3本の補正後長の最大)に
無音パド/トリムして出力する」を Stage 1 の出力仕様として明記。→ 設計 §5

### R-5: 話者間ラウドネス整合は loudnorm ではなく測定 + `volume` で行う

**落とし穴**: 中間段(Stage 2)の -20 LUFS 整合に「loudnorm 2パス(linear)」を使うと:

1. loudnorm は linear=true でも TP 制約でゲインが頭打ちになると**無告知でダイナミックモードに落ちる**。
   中間段で音を潰すのは、マスタリング設計で自ら排した失敗モードそのもの。
2. loudnorm は最重フィルタ(実測 53x)。話者3本 × 2パスで約 2.2分かかる。

**採用した設計**: ここで必要なのは「一定ゲインで -20 LUFS に置く」ことだけなので、`ebur128` で
Integrated を測定し `volume=<差分>dB` を適用する(純線形・決定論的・TP フォールバック無し)。
測定1パスで済み約1.1分短縮。ピーク管理は mix 入力ゲインと Stage 5 が担う。loudnorm の
2パス運用は最終マスタリング(Stage 5)専用とする。→ 設計 §7 Stage 2-7

### R-6: オフセット適用はサンプル単位指定にする

**落とし穴**: `adelay` のミリ秒指定は整数丸めで ±0.5ms の量子化誤差を持ち、残差目標 ±1ms の
半分を適用段だけで使い切る。

**採用した設計**: `adelay=<n>S`(サンプル数指定)/ `atrim=start_sample=<n>` を用い、適用誤差を
±0.5 サンプル(±10µs)に抑える。`S` サフィックスの挙動は対象 ffmpeg で実測確認する。→ 設計 §7 Stage 1-5

### R-7: `python-multipart` は削除できる(依存 4 → 3)

multipart が要るのはフォームエンコードの解析のみ。チャンクアップロードを
`application/octet-stream` の raw body(`await request.body()`)で受ければ不要。
チャンク方式(設計 §6.3)なら最初から multipart を使う局面がない。→ 設計 §3.2

### R-8: チャンク追記は `PUT` に統一

チャンク追記 API は冪等な位置指定書き込みなので、`POST` ではなく `PUT …/chunk?offset=` に統一。→ 設計 §8

## 留意事項(設計は変更せず、実装・運用で対応)

- **R-9: reference は VoIP 録音であり、ジッタバッファ適応による非線形な時間ジャンプが入りうる。**
  線形ドリフトモデル+外れ値除去付きフィットで概ね吸収できるが、残差 >±1ms 警告の原因候補として
  UI の警告文言に含める。区間別オフセット系列に不連続(>20ms の段差)があれば個別に警告する。→ 設計 §13.1
- **R-10: preview.opus 96kbps は NR の失敗モード(水中音)の判定には余裕が薄い。** Opus 96k は
  音声にはほぼ透明だが、A/B の目的が「アーティファクト検出」である cleanup ステージだけは
  ビットレートを上げる(128kbps、パラメータ化)。→ 設計 §13.2
- **R-11: `GET /download/{artifact}` はパス・トラバーサル対策必須。** artifact 名はホワイトリスト
  (project.json に記録された成果物名)との照合のみで解決し、パス結合をしない。→ 設計 §13.3
- **R-12: 将来の Web サービス化への影響は小さい。** 認証はリバースプロキシ層で後付け可能、
  ストレージはプロジェクトディレクトリ単位で独立しているためオブジェクトストレージへ移行可能、
  API は既に REST。現設計のまま進めてよい。ただし project-id はユーザー入力をそのままパスにせず
  生成 ID にする(R-11 と同根)。→ 設計 §13.4

## 是認(検討の上、変更不要と判断)

- バックエンド必須の論証(素材6本のデコードで 5,273MB > ブラウザのタブ上限)、
  DB/ジョブキュー/WebSocket/audalign の不採用理由: いずれも数値根拠が妥当。
- rubberband によるドリフト補正: atempo が ppm 級で無効という実測は決定的で、代替なし。
- `aloop` 回避(RAM 1.3GB 消費)と `-stream_loop` 方式、`amix normalize=0`、2段コンプ、
  2パス loudnorm(マスタのみ): 妥当。
- 容量設計 3.5GB・処理時間 10〜15分の見積り: 実測ベースで妥当。R-5 でさらに約1分短縮。
